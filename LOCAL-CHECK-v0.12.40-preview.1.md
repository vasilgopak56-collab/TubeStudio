# Отдельная проверка MCP v0.12.40-preview.1

Распакуйте исходники в новую папку, не поверх рабочей установки. Не переносите .env, рабочие данные, OAuth/ключи и приватные промпты. Ни для проверки нового параметра списка, ни для stdio не нужен провайдер. Нужны установленный Node.js/npm и Chromium/Chrome для веб-части тестов. Не запускайте smoke или платные генерации.

## Сборка и модульные проверки
Из корня проекта:
```powershell
npm ci
npm run typecheck
npm run build
npm run test:unit
npm run check:windows
```
Файловая проверка Windows не подтверждает нативный запуск. Модульные тесты создают временные синтетические данные и не наследуют провайдерские ключи. Артефакты dist и node_modules в ZIP не включены — их создают сборка и установка зависимостей.

## SDK/stdio и веб-конфигурация
После сборки задайте **реальный существующий** путь к своему Chrome. Пример PowerShell, путь может отличаться:
```powershell
$env:CHROME_PATH = "C:\Program Files\Google\Chrome\Application\chrome.exe"
node --test --test-concurrency=1 tests/e2e/mcp.test.mjs
```
Проверьте доступность loopback-портов 8804 и 8805: тесты используют их для локальной веб-части. Не создавайте фиктивные ссылки на браузер и не отключайте системную защиту. В Linux здесь прошли 9 сценариев этого файла; на Windows он не запускался, успех не обещается. Остальные файлы полного E2E этим не подтверждены.

Тесты используют официальный SDK, отдельный дочерний stdio-процесс и временную синтетическую папку. Веб-сервер получает ENV_FILE на отсутствующий файл и не наследует настоящие ключи. Фиктивные строки SECRET_SENTINEL и тестовый пароль — не реальные учётные данные. Браузерные запросы вне loopback блокируются. Клиент теста не является установленным внешним AI-клиентом и не отправляет текст модельному провайдеру. Для проверки чтения не нужен вход в Google/Notion.

Покрыто: 5 read-only инструментов, whitelist/scopes, UTF-16/токен записи, список и optional expectedListToken, STALE_LIST после изменения невыведенной записи без смены названия/даты, перезапуск чтения, стабильность между процессами, отсутствие записи/секретных полей, веб-конфигурация и opt-in profit, авторизация веб-маршрута, 390 px. При недоступности браузера начните с модульных тестов; не выдавайте их за stdio/веб-приёмку.

## Проверка вручную во внешнем клиенте — необязательно
Только с вашим явным решением подключить **доверенный локальный stdio-клиент**. Облачный HTTPS-only клиент к stdio напрямую не подключается. Его AI-обработка может тарифицироваться и передавать приватные тексты провайдеру; не используйте рабочие данные ради теста.

В отдельной тестовой установке следуйте MCP-README.md: выберите минимальные scopes, проверьте фактические пути Node/entrypoint/тестового DATA_DIR. Не добавляйте ключи в env MCP и не заменяйте конфигурацию других серверов вслепую. Новый процесс должен показывать version 0.12.40-preview.1.

1. Вызовите ts_list_saved с kind projects, offset 0, limit 1. В тестовой папке должны быть хотя бы две корректные синтетические записи; их формат есть в tests/e2e/mcp.test.mjs. Сохраните ответ целиком.
2. Следующая страница: offset из nextOffset и expectedListToken из listToken. Если nextOffset null, страницы закончились — не придумывайте offset.
3. Между вызовами измените **только синтетическую** просканированную запись в тестовом DATA_DIR: следующий запрос со старым expectedListToken должен вернуть STALE_LIST, без частичных строк.
4. Отбросьте накопленные страницы. Начните с offset 0 без expectedListToken; продолжайте с новым listToken.
5. Не путайте с snapshotToken/expectedToken чтения одной записи. Отдельные подробности и ограничения scanLimited/конкурентных изменений — MCP-README.md.

Ручной внешний клиент и нативный Windows здесь не проверены. Для калькулятора остаётся LOCAL-CHECK-v0.12.38-preview.1.md; его браузерная/визуальная приёмка всё ещё не выполнена. Для пауз сохранена LOCAL-CHECK-v0.12.39-preview.1.md. Итоги текущей версии перечислены в PREVIEW-CHECKS.json.
